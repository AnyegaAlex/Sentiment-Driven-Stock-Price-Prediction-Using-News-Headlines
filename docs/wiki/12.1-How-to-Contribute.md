**File:** `/wiki/12.1-How-to-Contribute.md`

## Overview

Tickflow is an open-source project, and contributions are welcome from developers, data scientists, traders, and enthusiasts. This page provides a comprehensive guide for contributing to the project, including finding issues, proposing features, the development workflow, testing requirements, and the pull request process.

All contributions are subject to the project's [Code of Conduct](12.2-Code-of-Conduct.md). By participating, you agree to abide by its terms.

## Finding Issues

### Issue Tracker

Issues are tracked on GitHub:  
[https://github.com/AnyegaAlex/Sentiment-Driven-Stock-Price-Prediction-Using-News-Headlines/issues](https://github.com/AnyegaAlex/Sentiment-Driven-Stock-Price-Prediction-Using-News-Headlines/issues)

### Issue Labels

| Label | Description |
|-------|-------------|
| **good first issue** | Beginner-friendly, good for first-time contributors |
| **help wanted** | Issues where assistance is needed |
| **bug** | Confirmed bugs |
| **enhancement** | Feature requests and improvements |
| **documentation** | Documentation-related tasks |
| **security** | Security vulnerabilities |

### Finding a Good First Issue

1. Visit the Issues page
2. Filter by label `good first issue`
3. Read the issue description and comments
4. Comment on the issue to indicate you are working on it
5. Wait for assignment or confirmation from a maintainer

## Feature Proposals

### Feature Request Template

Use the feature request template when opening an issue:

```markdown
---
name: Feature Request
about: Suggest a new feature for Tickflow
title: '[FEATURE] '
labels: enhancement
assignees: ''
---

## Feature Description
Clear description of the feature.

## Problem Statement
What problem does this feature solve?

## Proposed Solution
How should this feature be implemented?

## Alternatives Considered
Any alternative solutions considered.

## Additional Context
Any other relevant information.
```

### Feature Proposal Process

| Step | Description |
|------|-------------|
| **1. Open an Issue** | Use the feature request template |
| **2. Discussion** | Maintainers and community discuss feasibility |
| **3. Approval** | Feature is approved for development |
| **4. Development** | Implement the feature following the workflow |
| **5. Review** | Submit a pull request for review |
| **6. Merge** | Feature is merged and released |

## Development Workflow

### Branching Strategy

```
main (production)
  └── develop (integration)
       └── feature/feature-name
       └── fix/bug-description
       └── docs/update-description
```

### Workflow Steps

**1. Fork the Repository**

```bash
# Click "Fork" on GitHub
# Then clone your fork
git clone https://github.com/YOUR_USERNAME/Sentiment-Driven-Stock-Price-Prediction-Using-News-Headlines.git
cd sentiment_driven_stock_price_prediction_engine
```

**2. Set Up Development Environment**

Follow the [Development Environment](7.1-Development-Environment.md) guide.

**3. Create a Feature Branch**

```bash
# Ensure you are on develop
git checkout develop
git pull origin develop

# Create a new branch
git checkout -b feature/your-feature-name
# or
git checkout -b fix/your-bug-fix
```

**4. Make Changes**

- Write clean, tested code
- Follow [Coding Standards](7.3-Coding-Standards.md)
- Add tests for new functionality
- Update documentation as needed

**5. Commit Changes**

```bash
git add .
git commit -m "feat: add your feature description"
```

Commit message format:

```
<type>(<scope>): <subject>

<body>

<footer>
```

| Type | Description |
|------|-------------|
| **feat** | New feature |
| **fix** | Bug fix |
| **docs** | Documentation changes |
| **style** | Code style (formatting, semicolons) |
| **refactor** | Code refactoring |
| **perf** | Performance improvements |
| **test** | Adding or updating tests |
| **chore** | Maintenance tasks |

**6. Push to Your Fork**

```bash
git push origin feature/your-feature-name
```

**7. Open a Pull Request**

- Go to the original repository
- Click "New Pull Request"
- Select `develop` as the base branch
- Select your feature branch as the compare branch
- Fill in the pull request template

## Testing Requirements

### Backend Tests

Run backend tests before submitting a PR:

```bash
# Run all tests
python manage.py test

# Run specific app tests
python manage.py test authentication

# Run with coverage
pytest --cov=authentication --cov=stocks
```

### Frontend Tests

```bash
cd frontend

# Run all tests
npm test

# Run with coverage
npm test:coverage
```

### End-to-End Tests

```bash
npx playwright test
```

### Coverage Requirements

| Component | Target Coverage |
|-----------|-----------------|
| **Models** | 95% |
| **Serializers** | 95% |
| **Views** | 85% |
| **Utils** | 80% |
| **Frontend Components** | 70% |
| **Frontend Hooks** | 80% |

## PR Review Process

### Pull Request Template

```markdown
## Description
Brief description of the changes.

## Type of Change
- [ ] Bug fix
- [ ] New feature
- [ ] Breaking change
- [ ] Documentation update

## Testing
- [ ] Unit tests added/updated
- [ ] Integration tests added/updated
- [ ] Manual testing performed

## Checklist
- [ ] Code follows project style guidelines
- [ ] Self-review performed
- [ ] Documentation updated
- [ ] No new warnings or errors

## Related Issues
Closes #123
```

### Review Criteria

| Check | Description |
|-------|-------------|
| **Functionality** | Does the code work as expected? |
| **Style** | Does the code follow project style guidelines? |
| **Testing** | Are there tests for new functionality? |
| **Documentation** | Is the documentation updated? |
| **Performance** | Are there any performance concerns? |
| **Security** | Are there any security vulnerabilities? |
| **Error Handling** | Are errors properly handled? |

### Review Process Steps

1. **Submit PR** – Open a pull request against `develop`
2. **Automated Checks** – CI runs tests and linting
3. **Code Review** – Maintainers review the code
4. **Address Feedback** – Make requested changes
5. **Approval** – PR is approved by at least one maintainer
6. **Merge** – PR is merged into `develop`
7. **Release** – Changes are included in the next release
